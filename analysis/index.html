NextChapter · AI costs, search cache, job offers and fit scores¶

What this is. A data analysis of the NextChapter prototype (an AI outplacement platform: companies pay, people leaving a company use it to find their next role). It answers four product questions with pandas and SQL:

  1. How much does the AI cost, per feature, per active user per month and per complete career path?
  2. How much does the search cache save?
  3. Where do verified job offers come from: by city and by source (web search vs Adzuna)?
  4. How are fit scores distributed around the product threshold of 75?

Each result is tied to a product choice in Decisions, and its limits are listed in Limitations. The last section explains, line by line, the SQL that hides any group figure about fewer than 5 people on the company side.

Data. Six CSV files exported from Supabase (Postgres) by export.py, using only the analytics views of migration 0032_analisi.sql. They contain aggregated or anonymous data only: no emails, names, companies, job titles, URLs, CV or chat text. User ids are replaced by codes (U01, U02…) in order of first activity.

The segment column separates development (the app owner's tests and the *.test accounts used while building), demo (demo accounts and the synthetic people of the demo company programmes) and system (nightly jobs not tied to a user).

4. Cost per active user per month¶

An active user in a month is a user code with at least one AI call that month. The cost per active user is the month's spend divided by those users, per segment. The second month is partial (data up to the export).

6. Search cache savings¶

Every night, each user's career paths look for new job offers. If another user searched the same role in the same area in the last 3 days, the shared archive is reused (hit) and no new search is paid. Otherwise a real search runs (miss). Savings are estimated as hits × average cost of a miss.

In [8]:
hits, misses = cache_runs["cache_hits"].sum(), cache_runs["cache_misses"].sum()
miss_runs = cache_runs[cache_runs.cache_misses > 0]
cost_per_miss = miss_runs["cost_usd"].sum() / miss_runs["cache_misses"].sum()
saved = hits * cost_per_miss
hit_rate = hits / (hits + misses)

7. Verified offers by city and source¶

Only verified offers count here: the page was opened and checked as a real, single, open job ad. Cities are grouped into Italy (Milano, Brescia, Bergamo or country it) and United Kingdom (London or country gb).

ITALY_CITIES, UK_CITIES = {"Milano", "Brescia", "Bergamo"}, {"London"}
def market(row):
    if row.city in ITALY_CITIES or row.country == "it":
        return "Italy"
    if row.city in UK_CITIES or row.country == "gb":
        return "United Kingdom"
    return "Other / unknown"
jobs["market"] = jobs.apply(market, axis=1)

11. Appendix · The "5-person" threshold on the company side (SQL)¶

Companies see only group figures about the people in their transition programme, never individual data. A figure about fewer than 5 people could point to a person ("the only one in Finance who found a job"), so the database applies three rules before anything reaches the company dashboard. The code below is copied verbatim from the migrations (comments in Italian are the original ones).

Rule 1 · Publishing a count: kpi_publish (migration 0022)¶

Every night the true counts are computed, but the company sees a published copy that changes only in steps:

  • never published and below 5 → stays hidden (null);
  • never published and 5 or more → published;
  • already published → changes only when the true value has moved by at least 5.

The third rule stops "differencing": if a figure went from 12 to 13 overnight, the company could guess that one specific person just found a job. Moving in steps of 5 hides single changes.

In [13]:
display(Markdown("""```sql
-- Regola di pubblicazione di un conteggio: mai pubblicato e sotto 5 → resta non pubblicato; mai pubblicato e 5 o
-- più → si pubblica; già pubblicato → cambia solo se il vero si è spostato di almeno 5.
create function public.kpi_publish(p_old jsonb, p_true integer)
returns jsonb
language sql
immutable
set search_path = ''
as $$
  select case
    when p_old is null or p_old = 'null'::jsonb then case when p_true >= 5 then to_jsonb(p_true) else 'null'::jsonb end
    when abs(p_true - (p_old #>> '{}')::integer) >= 5 then to_jsonb(p_true)
    else p_old
  end;
$$;
```"""))

def kpi_publish(old, true):
    # Python twin of public.kpi_publish: old = currently published value (None = never published)
    if old is None:
        return true if true >= 5 else None
    return true if abs(true - old) >= 5 else old

Rule 2 · Showing a figure: employer_kpis (migration 0024)¶

When the dashboard asks for the figures, each published metric goes through a second filter:

case shown as why
the whole group (group) is below 5 hidden too few people to say anything
the metric is below 5 "fewer than 5" (lt5) small counts identify people
the people outside the metric are below 5 (group − v < 5) "at least 5" (atleast5) otherwise "18 of 19 found a job" reveals the one who did not
otherwise the number safe

The third case (the complement) was added in migration 0023: hiding small numbers is not enough if the remainder is small.

def show(metric, v, group):
    # Python twin of the CASE in public.employer_kpis
    if metric != "group" and (group is None or group < 5):
        return "hidden"
    if v is None or v < 5:
        return "fewer than 5"
    if metric != "group" and group - v < 5:
        return "at least 5"
    return v
